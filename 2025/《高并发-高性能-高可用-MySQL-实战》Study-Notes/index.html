数据库 vs Excel

已经有了电子表格，为什么需要数据库

  • 数据量对比
    • Excel 2003 之前最大行数是 65536 行，Excel 2007 之后最大行数是 1048576 行
    • 数据库理论上没有行数上限
    • 单机数据库若行数太多遇到性能问题，可以通过分库分表等技术解决
  • 结构化查询
    • 数据库有完备的结构化查询语言（SQL）
    • Excel也有结构化查询的功能（Microsoft Query），Excel结构化查询功能不如数据库强大
  • 服务化
    • Excel是文件级别的，直接面向终端用户
    • 数据库面向软件，提供软件接口
  • 事务
    • Excel没有事务，无法做到不同人的工作同时进行
    • 数据库事务是关系型数据库的核心优势
  • 分布式
    • Excel天生是单体的，面向文件的
    • 数据库具有主备复制、高可用、分布式等形态
  • 总结
    • Excel 面向个人，以文件为基础，处理的数据量有限，功能有限，拓展性差
    • 数据库面向软件，接口，处理数据量大，功能强大，事务支持，可拓展性好

MySQL的架构

  • MySQL的架构中，体现了分层架构，管道-过滤器架构，微核架构
  • 软件工程当中有很多经典的架构设计，大型软件往往不是使用单一的架构设计，而是多种混合
  • 研究问题要有清晰的视野，分清楚微观和宏观
  • 理论要灵活实践，不要死读书


客户端是怎样连接MySQL数据库的

TCP/IP连接报文可以作为其他C/S架构的参考

其他连接方式均限于本机连接，使用范围有限。

TCP/IP连接（最常用的连接方式）

  • 三次握手建立TCP连接

  • 认证连接

    • 服务端 → 客户端：发送握手初始化包
    • 客户端 → 服务端：发送验证
    • 服务端 → 客户端：认证结果消息

  • 认证通过之后，客户端开始与服务端之间交互

    • MySQL TCP通讯协议 —— 命令执行
      • 客户端 → 服务端：发送命令包（Command Packet）
      • 服务端 → 客户端：发送回应包

  • 断开MySQL连接

    • 客户端 → 服务器：发送退出命令包

  • 四次握手断开TCP连接

  • MySQL TCP报文格式

    • 消息头：3字节报文长度 + 1字节序号
    • 消息体：1字节指令 + 其余为参数
    • 指令举例：切换数据库（0x02）、查询命令（0x03）

命名管道

  • 同一台服务器通讯（Windows）
  • 命名管道开启方式：--enable-named-pipe

共享内存

  • 服务端配置：--shared-memory
  • 客户端配置：--protocol=memory

UNIX域套接字

  • 服务端配置：--socket=/tmp/mysql.sock
  • 客户端配置：-S /tmp/mysql.sock


一个SQL语句是怎样执行的

总结

  • SQL 语句的执行过程涉及 MySQL 的几乎所有模块：一个 SQL 语句按照：分析 → 优化 → 执行 → 落盘 的步骤执行
  • MySQL 8.0 之后已停用缓存功能
  • 不同存储引擎的执行方法不同

连接器

  • 起一个监听，连接客户端的请求

（查询）缓存

  • 之前执行过的语句会以 KV（键值对）形式缓存在内存中
  • 查询前会先查找是否有相同语句的缓存
  • 不推荐使用缓存：数据表一旦修改，会清除所有相关缓存
  • MySQL 8.0 之后已移除缓存功能

分析器

  • 分析器的作用是理解你要“干什么”
  • 先做词法分析，识别 SQL 语句中的关键字
  • 再做句法分析，判断 SQL 语句是否符合语法规则

优化器

  • 优化器的作用是知道“怎么做”
  • 主要工作是决定如何使用索引，以提高查询效率

执行器

  • 执行器的主要工作是校验权限、调用存储引擎
  • 首先校验用户对目标数据是否有权限
  • 以行为粒度调用存储引擎执行 SQL
  • 如果没有索引，执行器会逐行扫描所有数据

存储引擎

  • 存储引擎的任务是将执行器的指令落实到数据文件上
  • 不同存储引擎的原理和执行方式差异很大


MySQL有哪些存储引擎（四种常见的 MySQL 存储引擎）

MyISAM

对查询效率要求非常高的场景可考虑 MyISAM

  • MySQL 5.5.5 之前的默认存储引擎
  • 插入数据快，空间利用率高
  • 不支持事务

InnoDB

目前最主流的存储引擎，适合各种互联网业务

  • MySQL 5.5.5 之后的默认存储引擎
  • 支持事务、外键
  • 支持崩溃修复能力和并发控制

Memory

临时表可考虑使用 Memory

  • 所有数据存储在内存中，速度快
  • 数据安全性差（重启后数据丢失）

Archive

日志信息归档可考虑使用 Archive

  • 数据压缩，空间利用率高
  • 插入速度快
  • 不支持索引，查询性能差


第4章 如何建表更符合业务

索引组织表（Index Organized Table/IOT）

  • 索引组织表是一种把表的数据直接按索引（通常是主键）来存储的表。它把“索引结构”当作“表的数据存储结构”——不是先把行按普通堆表（heap）写入再建索引，而是把行存放在 B 树 索引节点中。这样主键顺序的范围查找、按主键排序的查询会非常高效
  • 优点：主键查找和主键范围扫描非常高效、节省部分存储、减少一次跳转
  • 缺点：主键更新/随机写入开销大、对宽行不友好、二级索引回表代价需要考虑
  • 适用场景：以主键访问为主、行较窄、主键稳定且尽可能顺序生成的表
  • 在不同数据库（Oracle、InnoDB、SQL Server）中都有类似概念，但实现和细节不同

基本原理（怎么存储的）

  • 在普通的**堆表（heap-organized table）**中：
    • 表的数据按插入顺序存放在数据块中（没有按某一列排序）
    • 索引（如 B 树）只是额外的结构，索引叶子存放指向数据行的指针（如 ROWID）
  • 在索引组织表中：
    • 数据本身以 B 树 索引的方式组织：主键值作为 B 树 排序键，行记录放在索引叶子节点
    • 叶子节点既是索引叶子，也是表的数据存储位置 —— 没有独立的堆区来存主键列的行（或说行的主副本就在索引里）


索引（Index）

  • 索引是数据库中对某一列或多个列的值进行预排序的数据结构
  • 索引可以理解为数据的“目录”
  • 在 InnoDB 中，主键是一个特殊索引字段


主键（Primary Key）

  • 在 InnoDB 存储引擎表中，每张表都有一个主键：
    • 若表中有一个非空唯一索引（Unique NOT NULL），即为主键
    • 若有多个非空唯一索引，选择第一个定义的索引
    • 若无，InnoDB 自动创建一个 6 字节的指针作为主键


主流索引查找算法

线性查找（Linear Search）

  • 时间复杂度：O(N)
  • 从第一个数据开始，逐个匹配

二分查找（Binary Search）

  • 时间复杂度：O(logN)
  • 拿出有序数列中点位置作为比较对象，根据中点数据大小，选取一半数据作为新的数列，每次可以将数据量减小一半

二叉查找树（Binary Search Tree）

  • 时间复杂度：O(logN)
  • 使用经典的二叉树数据结构，由根节点开始查找，可能退化为线性查找

平衡二叉树（AVL Tree）

  • 查找时与二叉搜索树相同，增删改时通过旋转操作维护树的平衡，AVL树可以保证不会退化成线性查找

B树（B Tree）

  • B树是线性数据结构和树的结合，通过多数据节点大大降低了树的高度，不需要旋转就可以保证树的平衡

B+树（B+ Tree）

  • 由B树发展而来的一种数据结构，所有数据均在叶子节点，所有数据形成了一个线性表（范围查找效率更高）
  • B+树是目前最主流的数据库索引算法
  • B+树由线性表、二叉树、B树发展而来
  • B+树集成了线性表、平衡二叉树的优势


为什么说InnoDB索引即数据

B+树索引

  • InnoDB 使用 B+ 树作为索引的数据结构
  • B+ 树的高度一般为 2–4 层，查找速度非常快
  • 在同层 B+ 树节点之间，为双向链表
  • 在 B+ 树节点之内，数据条目之间为单向链表
  • 所谓“索引即数据”，是把数据直接记录在了主索引里
  • InnoDB 索引分为聚簇索引（主索引）和辅助索引

聚簇索引（Clustered Index）

  • 根据表的主键构造一个 B+ 树
  • 叶子节点直接存放行数据，而不是指针
  • 在索引组织表中，数据也是 B+ 树的一部分

辅助索引（Secondary Index）

  • 每张表可以有多个辅助索引
  • 叶子节点并不包含行数据
  • 叶子节点记录了行数据的主键，用来指示数据位置

InnoDB数据表是如何存储的

tablespace

  • 表空间指数据表在磁盘上的存储区域
  • 默认所有表共享一个表空间；
  • 每张表的数据也可以开启独占表空间（.ibd文件）（推荐：容易迁移，备份管理）
  • 内部按用途再划分为：Leaf node segment、Non-Leaf node segment、Rollback segment 等

segment

  • 数据段：B+树叶子节点（存实际行数据）
  • 索引段：B+树非叶子节点（存目录项）
  • 段由InnoDB自动管理，一个段由若干连续/离散的区（extent）组成

extent

  • 由连续64个页构成，固定1 MB
  • 一次性向磁盘申请4-5个区，减少随机分配开销

page

  • page是InnoDB磁盘读写的最小逻辑单位，默认16 KB
  • 一个页即一个B+树节点（B+ Tree Node）
  • 页的大小充分考虑了机械硬盘和SSD的最小读写单元（512B/4KB）
  • 页内记录按槽（slot）组织，含行头信息（Trx id、Roll Pointer等）
  • InnoDB中的页是InnoDB自身的逻辑概念，与硬件的页无关
  • MySQL 从磁盘读取或写入数据时，不是一行一行地读写，而是 以页为单位（Page I/O），默认页大小：16KB（可配置为 4KB、8KB、32KB、64KB，但绝大多数系统使用16KB）
  • 页太大 → 浪费I/O与内存，降低并发；页太小 → 管理成本高，I/O放大；16KB 是在磁盘页（4KB）、系统内存、I/O 特性、B+树性能之间的一个最佳平衡点。
    几乎所有主流数据库（Oracle、PostgreSQL、SQL Server）也采用类似的默认页大小

为什么页不能太大（比如 16MB）?

I/O效率问题

  • 当 MySQL 访问一个页时，它会把整个页从磁盘加载到内存
  • 如果页非常大（例如 16MB），哪怕你只需要访问其中的一行数据，也必须把整个 16MB 都读入内存
  • 结果：
    • 浪费内存（Buffer Pool）
    • 浪费I/O带宽，延迟增加
    • 随机读性能极差

缓存粒度过粗

  • InnoDB 使用 Buffer Pool 缓存页。如果页太大：
    • 每个页就占用很大一块内存
    • 同样大小的 Buffer Pool 能缓存的页数就少
    • 缓存命中率大幅下降
    • 频繁的页替换导致性能抖动

并发冲突增大

  • 页是锁粒度的基础之一（比如行锁和页锁都与页相关）
  • 页越大，落在同一页的行越多，多个事务更容易竞争同一个页
  • 结果：
    • 行锁、页锁冲突频繁
    • 并发性能下降

崩溃恢复成本上升

  • 页越大，崩溃时需要重做（redo log）和回滚（undo log）的范围越大，恢复速度会明显变慢

结论：页太大 → I/O浪费、缓存命中率下降、并发差、恢复慢


为什么页不能太小（比如16B或512B）？

I/O放大严重

  • 磁盘 I/O（尤其是机械硬盘或 SSD）都是以扇区（4KB或更大）为单位读写的
  • 如果页太小，比如 16B，MySQL 每次读一个页时，底层也要进行一次4KB的I/O操作
  • 结果：
    • 读写开销增大（读了很多没用的数据）
    • 秒I/O请求数暴涨（IOPS需求上升）
    • 系统整体性能下降

元数据管理成本高

  • 每个页都需要维护：
    • 页头信息（Page Header）
    • 校验信息（Checksum）
    • 索引指针（B+树结构）
  • 结果：
    • 这些元数据有固定大小（几十字节），如果页只有16B，那开销比例极大！

B+树高度急剧上升

  • 索引存储使用B+树结构
  • 页越小 → 每个页能容纳的键值对越少 →
  • 要存下同样的数据，需要更多层级 →
  • 树高度上升 → 查询路径更长，性能变差

页管理复杂度增加

  • 页太多（比如16B页意味着一张1GB的表要几十亿页）
  • 那么：
    • Page Directory、Free List、Buffer Pool 管理表都会爆炸
    • 事务日志、双写缓冲的同步压力增大
    • CPU开销上升

页太小 → I/O放大、元数据浪费、索引变深、CPU压力大
