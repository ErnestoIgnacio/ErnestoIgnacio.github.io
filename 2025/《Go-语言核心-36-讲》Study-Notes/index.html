模块一：Go语言基础知识 (6讲)

01 | 工作区和GOPATH

知识点

  • GOROOT：Go 语言安装根目录的路径，也就是 GO 语言的安装路径
  • GOPATH：若干工作区目录的路径。是我们自己定义的工作空间
  • GOBIN：GO 程序生成的可执行文件（executable file）的路径

问题：你知道设置 GOPATH 有什么意义吗？

  • 典型回答：
    • 可以把 GOPATH 简单理解成 Go 语言的工作目录，它的值是一个目录的路径，也可以是多个目录路径，每个目录都代表 Go 语言的一个工作区（workspace）
    • 我们需要利用这些工作区，去放置 Go 语言的源码文件（source file），以及安装（install）后的归档文件（archive file，也就是以“.a”为扩展名的文件）和可执行文件（executable file）
  • 扩展：

由于 Go 语言项目在其生命周期内的所有操作（编码、依赖管理、构建、测试、安装等）基本上都是围绕着 GOPATH 和工作区进行的。所以，它的背后至少有 3 个知识点，分别是：

  1. Go 语言源码的组织方式是怎样的；
  2. 你是否了解源码安装后的结果（只有在安装后，Go 语言源码才能被我们或其他代码使用）；
  3. 你是否理解构建和安装 Go 程序的过程（这在开发程序以及查找程序问题的时候都很有用，否则你很可能会走弯路）。

Go 语言源码的组织方式

  • Go 语言源码的组织方式就是以环境变量 GOPATH、工作区、src 目录和代码包为主线的

了解源码安装后的结果

  • 源码文件通常会被放在某个工作区的 src 子目录下
  • 在安装后如果产生了归档文件（以“.a”为扩展名的文件），就会放进该工作区的 pkg 子目录；
  • 如果产生了可执行文件，就可能会放进该工作区的 bin 子目录
  • 归档文件的相对目录与 pkg 目录之间还有一级目录，叫做平台相关目录。平台相关目录的名称是由 build（也称“构建”）的目标操作系统、下划线和目标计算架构的代号组成的。比如，构建某个代码包时的目标操作系统是 Linux，目标计算架构是 64 位的，那么对应的平台相关目录就是 linux_amd64

理解构建和安装 Go 程序的过程

  • 构建

    • go build
    • 如果构建的是库源码文件，那么操作后产生的结果文件只会存在于临时目录中。这里的构建的主要意义在于检查和验证
    • 如果构建的是命令源码文件，那么操作的结果文件会被搬运到源码文件所在的目录中

  • 安装

    • go install
    • 安装操作会先执行构建，然后还会进行链接操作，并且把结果文件搬运到指定目录
    • 如果安装的是库源码文件，那么结果文件会被搬运到它所在工作区的 pkg 目录下的某个子目录中
    • 如果安装的是命令源码文件，那么结果文件会被搬运到它所在工作区的 bin 目录中，或者环境变量GOBIN指向的目录中

  • 构建和安装代码包的时候都会执行编译、打包等操作，并且，这些操作生成的任何文件都会先被保存到某个临时的目录中


思考题

Go 语言在多个工作区中查找依赖包的时候是以怎样的顺序进行的？

  • 传统 GOPATH 模式
    • 在 GOPATH 模式 下，Go 语言允许设置多个工作区，也就是 GOPATH 可以用冒号（Linux/macOS）或者分号（Windows）分隔多个路径，这时候 Go 会按照 GOPATH 中 从左到右的顺序 依次查找依赖包，这个顺序在 Go 编译器内部是严格依次匹配的，第一个找到的就用，不会继续往后找
  • Go Modules 模式（推荐）
    • 从 Go 1.11（模块引入）开始，如果启用了模块（即有 go.mod 文件），情况就不一样了：
      • Go 先只看你的模块依赖（写在 go.mod 的 require 中）
      • 如果你的模块依赖还缺少，就会去 GOPATH 的 pkg/mod 下看，也就是缓存
      • 如果本地都没有，就到远程拉取依赖（例如 proxy.golang.org 或者自定义的私有代理）
    • 在 Modules 模式下，GOPATH 只被当做依赖缓存目录，代码的查找不再依赖 GOPATH/src 的多工作区顺序，而是以 go.mod 中列出的依赖为准

如果在多个工作区中都存在导入路径相同的代码包会产生冲突吗？

  • GOPATH 模式 下
    • GOPATH 配置了多个工作区，不会冲突，但会按照顺序只选第一个匹配的。所以看上去不会报错冲突，但是你如果在两个工作区下放了相同路径的不同版本，可能会因为优先级不同而导致版本混乱。这就是为什么在多个 GOPATH 时要非常小心，不要重复放相同 import path 的包。
  • Go Modules 模式 下
    • 如果你使用 Modules（即 go.mod），那导入路径就是唯一标识，版本信息由 go.mod 确定
      • 同一个包，只能有一个版本
      • 模块下载到 GOPATH/pkg/mod 中以模块版本号区分，不存在路径冲突
      • Go Modules 的机制保证不会因为同名包导致冲突

深入理解GO PATH

  • Go 1.11以前：
    • GOPATH 是 Go 语言的一个工作区（workspace）概念，主要用来告诉 Go 工具链：Go 代码（src）、编译好的包（pkg）、以及可执行文件（bin）应该放在哪里
  • Go Modules 出现以后（Go 1.11+）
    • 一般都用 Go Modules（go.mod 文件）。这时 GOPATH 只是一个默认的包缓存目录，你就可以在任意地方写代码，不再要求所有代码必须放在 GOPATH/src 里面


02 | 命令源码文件

  • 环境变量 GOPATH 指向的是一个或多个工作区，每个工作区中都会有以代码包为基本组织形式的源码文件，这里的源码文件又分为三种（它们都有着不同的用途和编写规则），即：
    • 命令源码文件
    • 库源码文件
    • 测试源码文件

问题：命令源码文件的用途是什么，怎样编写它？

  • 命令源码文件是程序的运行入口，是每个可独立运行的程序必须拥有的。我们可以通过构建或安装，生成与其对应的可执行文件，后者一般会与该命令源码文件的直接父目录同名。
  • 如果一个源码文件声明属于main包，并且包含一个无参数声明且无结果声明的main函数，那么它就是命令源码文件
  • 对于一个独立的程序来说，命令源码文件永远只会也只能有一个

思考题

Q：默认情况下，我们可以让命令源码文件接受哪些类型的参数值？

默认情况下，Go 命令源码文件只能拿到 []string，也就是字符串参数。

但是用 flag 包，就能非常方便地转换成 int、bool、float64 等常用基础类型。

如果要做多命令或非常复杂的结构，就推荐 cobra 等库。

Go 标准库里对 命令源码文件（也就是可执行程序）支持命令行参数的方式主要有这几种：

  • （1）通过 os.Args
    • 这是最底层、最简单的方式：
      • os.Args 是一个 []string，默认包含命令本身以及传入的参数
      • 类型就是 字符串数组，也就是说所有的参数默认都是字符串
  • （2） 通过 flag 标准库
    • Go 内置的 flag 包，允许你更方便地从命令行获取参数，并自动做基本类型转换。默认支持：string、int、int64、uint、uint64、bool、float64
  • （3）如果需要更复杂的参数
    • 如果你需要：子命令、多级嵌套、复杂的参数格式就可以用更专业的命令行库（它们在 Go 社区里非常流行，允许你做更复杂的参数结构，但底层本质仍然是从字符串（os.Args）解析成你需要的 Go 类型），比如：
      • cobra
      • urfave/cli
      • kingpin

我们可以把自定义的数据类型作为参数值的类型吗？如果可以，怎样做？

  • 只要让你的类型实现 flag.Value 接口，就可以


03 | 库源码文件

基础概念知识

  • 库源码文件是不能被直接运行的源码文件，它仅用于存放程序实体，这些程序实体可以被其他代码使用（只要遵从 Go 语言规范的话）
  • 同目录下的源码文件的代码包声明语句要一致
  • 源码文件声明的代码包的名称可以与其所在的目录的名称不同。在针对代码包进行构建时，生成的结果文件的主名称与其父目录的名称一致
  • 名称的首字母为大写的程序实体才可以被当前包外的代码引用，否则它就只能被当前包内的其他代码引用。
  • Go 语言自然地把程序实体的访问权限划分为了包级私有的和公开的。对于包级私有的程序实体，即使你导入了它所在的代码包也无法引用到它。
  • 在 Go 1.5 及后续版本中，我们可以通过创建internal代码包让一些程序实体仅仅能被当前模块中的其他代码引用。这被称为 Go 程序实体的第三种访问权限：模块级私有。
    • internal代码包中声明的公开程序实体仅能被该代码包的直接父包及其子包中的代码引用。（引用前需要先导入这个internal包）

思考题

  • 如果会产生冲突，那么怎样解决这种冲突，有几种方式？

在 Go 语言中，包名（package name）是由 package 声明指定的，而导入路径（import path）是用来告诉编译器从哪里找到这个包。
