前置篇：心定之旅 (2讲)

01｜前世今生：你不得不了解的Go的历史和现状

开始接触一门新语言（技术）的时候，一定要去了解它的历史和现状，这样才能建立整体认知，了解它的未来走向。也建立“安全感”，相信它能够带来足够的价值与收益，更坚定的学习下去

Go 语言是怎样诞生的？

  • Go 语言的三位创始人
    • 肯·汤普森（Ken Thompson）（图灵奖获得者、C 语法联合发明人、Unix 之父）
    • 罗伯·派克（Rob Pike）（Plan 9 操作系统领导者、UTF-8 编码的最初设计者）
    • 罗伯特·格瑞史莫（Robert Griesemer）（Java 的 HotSpot 虚拟机和 Chrome 浏览器的 JavaScript V8 引擎的设计者之一）
  • Go语言诞生背景
    • 2007 年 9 月 20 日下午的一次普通讨论
    • 当时的谷歌内部主要使用 C++ 语言构建各种系统，但 C++ 的巨大复杂性、编译构建速度慢以及在编写服务端程序时对并发支持的不足
  • Go语言设计思路
    • 在 C 语言的基础上，修正一些明显的缺陷，删除一些被诟病较多的特性，增加一些缺失的功能
  • 2021 年。经过了十余年的打磨与优化，如今的 Go 语言已经逐渐成为了云计算时代基础设施的编程语言

思考题：

相较于传统的静态编译型编程语言（如 C、C++），Go 做出了哪些改进？

  • 简化语法、减少复杂性
    • Go 的语法风格接近 C，但砍掉了很多 C++ 里的“复杂特性”，例如继承、多重继承、模板（泛型只在后期引入），以 组合代替继承，避免“过度设计”
    • 没有头文件（.h/.cpp分离），一个 .go 文件就能包含可见的结构与函数定义，极大简化编译依赖
    • 严格的代码风格（比如 gofmt），避免团队协作中风格混乱
  • 内置并发支持
    • C/C++ 的多线程需要 pthread 或第三方库，且容易出错
    • Go 原生就设计了 goroutine（轻量线程）、channel（通信机制），使并发编程更易读、更安全，且跨平台无痛。
  • 自动垃圾回收
    • C/C++ 程序员必须手动管理内存，容易造成内存泄漏
    • Go 自带高效垃圾回收器，程序员只需要关注“什么时候分配”，不必关心“什么时候释放”
  • 快速编译，单文件可执行
    • Go 保留静态编译的优点（输出一个可移植的二进制文件）
    • 同时极大提升了编译速度，远超 C/C++ 链接的复杂性，Go 编译器往往几秒就完成
    • 编译结果就是一个无需额外依赖的二进制包，便于跨平台部署
  • 内置强大标准库
    • Go 标准库极其丰富：网络、并发、加密、Web，几乎一应俱全
    • 在 C/C++ 中通常要依赖第三方库或系统库
  • 包管理更现代
    • C/C++ 的包管理比较混乱（Makefile/CMake/各种包管理器）
    • Go 从 1.11 开始内置 go mod，模块化管理清晰且简洁
  • 更现代化的错误处理
    • Go 的 error 接口替代了传统的 errno 或异常机制
    • 明确返回错误值，避免隐藏式异常
    • 使得代码更容易读懂和调试
  • 跨平台和云原生友好
    • C/C++ 做跨平台需要针对不同架构编译、处理很多细节
    • Go 出生就支持跨平台编译，且对容器/微服务非常友好，部署一个可执行文件就能跑


02｜拒绝“Hello and Bye”：Go语言的设计哲学是怎么一回事？

简单

  • Go 语言的设计者们在语言设计之初，就拒绝了走语言特性融合的道路，选择了“做减法”并致力于打造一门简单的编程语言
  • 简单意味着可以使用更少的代码实现相同的功能；简单意味着代码具有更好的可读性，而可读性好的代码通常意味着更好的可维护性以及可靠性。
  • 都意味着对生产效率提升的极大促进，我们可以认为简单的设计哲学是 Go 生产力的源泉。

显式

  • Go 不允许不同类型的整型变量进行混合计算，它同样也不会对其进行隐式的自动转换。
  • Go 希望开发人员明确知道自己在做什么
  • Go 设计者所崇尚的显式哲学还直接决定了 Go 语言错误处理的形态：Go 语言采用了显式的基于值比较的错误处理方案

组合

  • 组合原则的应用实质上是塑造了 Go 程序的骨架结构。类型嵌入为类型提供了垂直扩展能力，而接口是水平组合的关键

并发

  • 面向多核、原生支持并发
  • Go 放弃了传统的基于操作系统线程的并发模型，而采用了用户层轻量级线程，Go 将之称为 goroutine
  • 在语言层面内置了辅助并发设计的原语：channel 和 select。开发者可以通过语言内置的 channel 传递消息或实现同步，并通过 select 实现多路 channel 的并发控制

面向工程

  • 将解决工程问题作为 Go 的设计原则之一去考虑

04｜初窥门径：一个Go程序的结构是怎样的？

  • 当运行一个可执行的 Go 程序的时候，所有的代码都会从这个main入口函数开始运行
  • 标准 Go 代码风格使用 Tab 而不是空格来实现缩进的
  • import “fmt” 一行中“fmt”代表的是包的导入路径（Import），它表示的是标准库下的 fmt 目录
  • fmt.Println 函数调用一行中的“fmt”代表的则是包名。
  • Go 源码文件本身采用的是 Unicode 字符集，而且用的是 UTF-8 标准的字符编码方式，这与编译后的程序所运行的环境所使用的字符集和字符编码方式是一致的。
  • Go 包是 Go 语言的基本组成单元。一个 Go 程序就是一组包的集合，所有 Go 代码都位于包中；
  • Go 源码可以导入其他 Go 包，并使用其中的导出语法元素，包括类型、变量、函数、方法等，而且，main 函数是整个 Go 应用的入口函数；
  • Go 源码需要先编译，再分发和运行。如果是单 Go 源文件的情况，我们可以直接使用 go build 命令 +Go 源文件名的方式编译。不过，对于复杂的 Go 项目，我们需要在 Go Module 的帮助下完成项目的构建。


05｜标准先行：Go项目的布局标准是什么？

生产环境中，go项目的项目布局是复杂的，go开发者必须熟悉go的项目布局

Go 语言“创世项目”结构的演化

  • Go 1.3 版本
    • （1）以 all.bash 为代表的代码构建的脚本源文件放在了 src 下面的顶层目录下
    • （2）src 下的二级目录 cmd 下面存放着 Go 相关可执行文件的相关目录，其中每个子目录都是一个 Go 工具链命令或子命令对应的可执行文件
    • （3） src 下的二级目录 pkg 下面存放着运行时实现、标准库包实现，这些包既可以被上面 cmd 下各程序所导入，也可以被 Go 语言项目之外的 Go 程序依赖并导入
  • 演进一：Go 1.4 版本删除 pkg 这一中间层目录并引入 internal 目录
    • 删除了 Go 源码树中“src/pkg/xxx”中 pkg 这一层级目录而直接使用 src/xxx（好处：Go 语言项目的源码树深度减少一层，更便于 Go 开发者阅读和探索 Go 项目源码）
    • Go 1.4 引入 internal 包机制，增加了 internal 目录；根据 internal 机制的定义，一个 Go 项目里的 internal 目录下的 Go 包，只可以被本项目内部的包导入。项目外部是无法导入这个 internal 目录下面的包的（好处：让一个 Go 项目中 Go 包的分类与用途变得更加清晰）
  • 演进二：Go1.6 版本增加 vendor 目录
    • Go 源码的编译可以不在 GOPATH 环境变量下面搜索依赖包的路径，而在 vendor 目录下查找对应的依赖包（解决 Go 包依赖版本管理的问题）
    • Go 1.6 版本中增加了 vendor 目录以支持 vendor 构建（让 Go 项目第一次具有了可重现构建（Reproducible Build）的能力）
  • 演进三：Go 1.13 版本引入 go.mod 和 go.sum
    • 引入了 Go Module 构建机制：在项目引入 go.mod 以及在 go.mod 中明确项目所依赖的第三方包和版本，项目的构建就将摆脱 GOPATH 的束缚，实现精准的可重现构建（为了解决 Go 包依赖版本管理的问题，Go 语言项目自身所依赖的包在 go.mod 中都有对应的信息，而原本这些依赖包是缓存在 vendor 目录下的）

这三次演进主要体现在简化结构布局，以及优化包依赖管理方面，起到了改善 Go 开发体验的作用。

Go 创世项目的源码布局以及演化对 Go 社区项目的布局具有重要的启发意义，以至于在多年的 Go 社区实践后，Go 社区逐渐形成了公认的 Go 项目的典型结构布局。


现在的 Go 项目的典型结构布局是怎样的？

一个 Go 项目通常分为可执行程序项目和库项目

Go 可执行程序项目的典型结构布局

  • cmd 目录
    • 存放项目要编译构建的可执行文件对应的 main 包的源文件
    • 项目中有多个可执行文件需要构建，每个可执行文件的 main 包单独放在一个子目录中
    • 通常来说，main 包应该很简洁。我们在 main 包中会做一些命令行参数解析、资源初始化、日志设施初始化、数据库连接初始化等工作，之后就会将程序的执行权限交给更高级的执行控制对象。
  • pkgN 目录
    • 存放项目自身要使用、同样也是可执行文件对应 main 包所要依赖的库文件，同时这些目录下的包还可以被外部项目引用
  • go.mod 和 go.sum
    • Go 语言包依赖管理使用的配置文件
  • vendor 目录
    • 可以将 vendor 目录视为一个可选目录，Go Module 本身就支持可再现构建，而无需使用 vendor

Go 库项目的典型结构布局

不推荐在项目中放置 vendor 目录去缓存库自身的第三方依赖，库项目仅通过 go.mod 文件明确表述出该项目依赖的 module 或包以及版本要求就可以了

注意早期 Go 可执行程序项目的典型布局

原本放在项目顶层目录下的 pkg1 和 pkg2 公共包被统一聚合到 pkg 目录下了



06｜构建模式：Go是怎么解决包依赖管理问题的？

Go 构建模式是怎么演化的？

  • 什么是Go建构
    • Go 程序由 Go 包组合而成的，Go 程序的构建过程就是确定包版本、编译包以及将编译后得到的目标文件链接在一起的过程
  • Go 语言的构建模式历经了三个迭代和演化过程
    • GOPATH
    • 1.5 版本的 Vendor 机制
    • 现在的 Go Module

GOPATH

  • Go 语言在首次开源时，就内置了一种名为 GOPATH 的构建模式

  • Go 编译器可以在本地 GOPATH 环境变量配置的路径下，搜寻 Go 程序依赖的第三方包。如果存在，就使用这个本地包进行编译；如果不存在，就会报编译错误。

  • Go 编译器在 GOPATH 构建模式下，究竟怎么在 GOPATH 配置的路径下搜寻第三方依赖包呢？

    export GOPATH=/usr/local/goprojects:/home/tonybai/go

    在 GOPATH 构建模式下，Go 编译器在编译 Go 程序时，就会在下面两个路径下搜索第三方依赖包是否存在：

    /usr/local/goprojects/src/github.com/user/repo /home/tonybai/go/src/github.com/user/repo

    没有显式设置 GOPATH 环境变量，Go 会将 GOPATH 设置为默认值，不同操作系统下默认值的路径不同，在 macOS 或 Linux 上，它的默认值是 $HOME/go。

  • 通过 go get 命令将本地缺失的第三方依赖包下载到本地：go get github.com/sirupsen/logrus

  • go get 命令，不仅能将 logrus 包下载到 GOPATH 环境变量配置的目录下，它还会检查 logrus 的依赖包在本地是否存在，如果不存在，go get 也会一并将它们下载到本地。

  • go get 下载的包只是那个时刻各个依赖包的最新主线版本

    会给后续 Go 程序的构建带来一些问题。比如，依赖包持续演进，可能会导致不同开发者在不同时间获取和编译同一个 Go 包时，得到不同的结果，也就是不能保证可重现的构建（Reproduceable Build）。又比如，如果依赖包引入了不兼容代码，程序将无法通过编译。

  • 在 GOPATH 构建模式下，Go 编译器实质上并没有关注 Go 项目所依赖的第三方包的版本

vendor 机制

  • vendor 机制本质上就是在 Go 项目的某个特定目录下，将项目的所有依赖包缓存起来，这个特定目录名就是 vendor
  • Go 编译器会优先感知和使用 vendor 目录下缓存的第三方包版本，而不是 GOPATH 环境变量所配置的路径下的第三方包版本。这样，无论第三方依赖包自己如何变化，无论 GOPATH 环境变量所配置的路径下的第三方包是否存在、版本是什么，都不会影响到 Go 程序的构建。
  • 如果你将 vendor 目录和项目源码一样提交到代码仓库，那么其他开发者下载你的项目后，就可以实现可重现的构建。因此，如果使用 vendor 机制管理第三方依赖包，最佳实践就是将 vendor 一并提交到代码仓库中。
  • 在添加完 vendor 后，我们重新编译 main.go，这个时候 Go 编译器就会在 vendor 目录下搜索程序依赖的 logrus 包以及后者依赖的 golang.org/x/sys/unix 包了。
  • 要想开启 vendor 机制，你的 Go 项目必须位于 GOPATH 环境变量配置的某个路径的 src 目录下面。如果不满足这一路径要求，那么 Go 编译器是不会理会 Go 项目目录下的 vendor 目录的。
  • vendor 机制虽然一定程度解决了 Go 程序可重现构建的问题，但对开发者来说，它的体验却不那么好。
    • Go 项目必须放在 GOPATH 环境变量配置的路径下，庞大的 vendor 目录需要提交到代码仓库，不仅占用代码仓库空间，减慢仓库下载和更新的速度，而且还会干扰代码评审，对实施代码统计等开发者效能工具也有比较大影响。
    • 还需要手工管理 vendor 下面的 Go 依赖包，包括项目依赖包的分析、版本的记录、依赖包获取和存放，等等，最让开发者头疼的就是这一点。

为了解决这个问题，Go 核心团队与社区将 Go 构建的重点转移到如何解决包依赖管理上。Go 社区先后开发了诸如 gb、glide、dep 等工具，来帮助 Go 开发者对 vendor 下的第三方包进行自动依赖分析和管理，但这些工具也都有自身的问题。

Go 核心团队基于社区实践的经验和教训，推出了 Go 官方的解决方案：Go Module。

Go Module

  • 从 Go 1.11 版本开始，除了 GOPATH 构建模式外，Go 又增加了一种 Go Module 构建模式。
  • 一个 Go Module 是一个 Go 包的集合。module 是有版本的，所以 module 下的包也就有了版本属性。这个 module 与这些包会组成一个独立的版本单元，它们一起打版本、发布和分发。
  • 在 Go Module 模式下，通常一个代码仓库对应一个 Go Module。一个 Go Module 的顶层目录下会放置一个 go.mod 文件，每个 go.mod 文件会定义唯一一个 module，也就是说 Go Module 与 go.mod 是一一对应的。
  • go.mod 文件所在的顶层目录也被称为 module 的根目录，module 根目录以及它子目录下的所有 Go 包均归属于这个 Go Module，这个 module 也被称为 main module。

08｜入口函数与包初始化：搞清Go程序的执行次序

main.main 函数：Go 应用的入口函数

  • main 包中的 main 函数，所有 Go 可执行程序的用户层执行逻辑的入口函数
  • Go 语言要求：可执行程序的 main 包必须定义 main 函数，否则 Go 编译器会报错（在启动了多个 Goroutine（Go 语言的轻量级用户线程，后面我们会详细讲解）的 Go 应用中，main.main 函数将在 Go 应用的主 Goroutine 中执行）
  • main 包的 main 函数，它虽然是用户层逻辑的入口函数，但它却不一定是用户层第一个被执行的函数。

init 函数：Go 包的初始化函数

  • Go 语言还有一个特殊函数，它就是用于进行包初始化的 init 函数
  • 如果 main 包依赖的包中定义了 init 函数，或者是 main 包自身定义了 init 函数，那么 Go 程序在这个包初始化的时候，就会自动调用它的 init 函数，因此这些 init 函数的执行就都会发生在 main 函数之前。
  • 在 Go 程序中我们不能手工显式地调用 init，否则就会收到编译错误
  • Go 包可以拥有不止一个 init 函数，每个组成 Go 包的 Go 源文件中，也可以定义多个 init 函数
