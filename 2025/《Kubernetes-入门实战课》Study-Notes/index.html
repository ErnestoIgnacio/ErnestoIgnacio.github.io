开篇词 (2讲)

开篇词｜迎难而上，做云原生时代的弄潮儿

  • 现在 Kubernetes 已经没有了实际意义上的竞争对手，成为了事实上的云原生操作系统，是构建现代应用的基石

  • 现代应用是什么？

    是微服务，是服务网格，这些统统要围绕着容器来开发、部署和运行，而使用容器就必然要用到容器编排技术，在现在只有唯一的选项，那就是 Kubernetes

  • 学习 Kubernetes 有哪些难点（Kubernetes 技术栈的特点）

    新：Kubernetes 用到的基本上都是比较前沿、陌生的技术，而且版本升级很快，经常变来变去

    广：Kubernetes 涉及的应用领域很多、覆盖面非常广，不太好找到合适的切入点或者突破口

    杂：Kubernetes 的各种实现比较杂乱，谁都可以上来“掺和”一下，让人看的眼晕

    深：Kubernetes 面对的每个具体问题和方向，都需要有很深的技术背景和底蕴，想要吃透很不容易

  • 学习方法论

    学习 Kubernetes 最好的方式是尽快建立一个全局观和大局观，等到你对这个陌生领域的全貌有了粗略但完整的认识之后，再挑选一个自己感兴趣的方向去研究，才是性价比最高的做法

    初级篇：熟悉Kubernetes发展的前因后果，基本架构；学习 YAML 语言、核心对象 Pod，还有离线业务对象 Job/CronJob、配置信息对象 ConfigMap/Secret。

    中级篇：使用 kubeadm 搭建出一个多节点的集群，模拟真实的生产环境，并介绍 Kubernetes 里的 4 个重要概念：Deployment、DaemonSet、Service、Ingress。明白 Kubernetes 的优点、特点是什么，知道为什么它能够一统天下，成为云原生时代的操作系统。

    高级篇：深层次知识点和高级应用技巧，包括持久化存储、有状态的对象、应用的滚动更新和自动伸缩、容器和节点的管理等等。

入门篇 (8讲)

01｜初识容器：万事开头难

Docker 的诞生

2013 年 3 月 15 日，在北美的圣克拉拉市召开了一场 Python 开发者社区的主题会议 PyCon，研究和探讨各种 Python 开发技术和应用。当天的会议日程快结束时，有一个“闪电演讲”（lighting talk）的小环节。其中有一位开发者，用了 5 分钟的时间，做了题为 “The future of Linux Containers” 的演讲。这个只有短短 5 分钟的技术演示，就是我们目前所看到的、席卷整个业界的云原生大潮的开端。正是在这段演讲里，Solomon Hykes（dotCloud 公司，也就是 Docker 公司的创始人）首次向全世界展示了 Docker 技术。

PyCon2013 大会之后，许多人都意识到了容器的价值和重要性，发现它能够解决困扰了云厂商多年的打包、部署、管理、运维等问题，Docker 也就迅速流行起来，成为了 GitHub 上的明星项目。然后在几个月的时间里，Docker 更是吸引了 Amazon、Google、Red Hat 等大公司的关注，这些公司利用自身的技术背景，纷纷在容器概念上大做文章，最终成就了我们今天所看到的至尊王者 Kubernetes 的出现。


Docker 的形态

  • Docker Desktop

    完全免费，但只能在 Linux 上运行，只能使用命令行操作，缺乏辅助工具，需要我们自己动手 DIY 运行环境。

    是现在各个公司在生产环境中实际使用的 Docker 产品

  • Docker Engine

    专门针对个人使用而设计的，支持 Mac 和 Windows 快速安装，具有直观的图形界面，还集成了许多周边工具，方便易用。


Docker 的安装

  • 操作 Docker 必须要有 root 权限，而直接使用 root 用户不够安全，加入 Docker 用户组是一个比较好的选择，这也是 Docker 官方推荐的做法

Docker 的架构

  • Client

    与 Docker Engine 里的后台服务 Docker daemon 通信

    Docker client 可以通过 build、pull、run等命令向 Docker daemon 发送请求

  • Docker Engine

    是容器和镜像的“大管家”，负责从远端拉取镜像、在本地存储镜像，还有从镜像生成容器、管理容器等所有功能。

    • Images：则存储在远端的仓库 Registry 里，客户端并不能直接访问镜像仓库。
    • Docker daemon：真正干活的其实是默默运行在后台的 Docker daemon

  • Registry

Docker Engine 是典型的客户端 / 服务器（C/S）架构，命令行工具 Docker 直接面对用户，后面的 Docker daemon 和 Registry 协作完成各种功能。

思考题

    1. 学完了这节课，你对容器技术和 Docker 有什么样的认识和感受？

    容器是一种沙盒技术

    1. Docker Engine 为什么要设计成客户端 / 服务器（C/S）架构？它有什么样的好处？

    • （1）解耦与灵活性

      客户端 (docker 命令行工具) 和 服务端 (dockerd 守护进程) 是解耦的，便于分别开发、测试、部署

      可以在一台机器上运行 Docker 客户端，通过网络连接另一台主机上的 Docker 服务端。

      好处：

      客户端可以远程控制多个 Docker 守护进程（适合管理多节点环境）。

      可以为不同的接口（CLI、API、Web UI）复用同一个守护进程。

    • （2）统一接口（REST API）

      Docker 守护进程对外暴露的是一套 RESTful API，任何支持 HTTP 请求的工具（包括 Docker CLI、Postman、curl 等）都可以与 Docker 交互。

      好处：

      提高可扩展性和可维护性。

      更容易构建自定义工具或图形化管理面板。

    • （3）安全性与权限控制

      通过 C/S 架构，服务端可以运行在具有更高权限的用户下（如 root），而客户端不需要。

      好处：

      控制不同用户对 Docker 的访问权限（例如用 socket、TLS、认证等方式）。

      可以部署安全网关或反向代理来保护 Docker API。

    • （4）跨平台与远程管理

      Docker 客户端可以在不同平台（如 Windows、macOS）运行，并连接运行在 Linux 上的 Docker 守护进程。

      好处：

      实现平台无关的开发与部署。

      本地开发 + 远程部署成为可能。

    • （5）便于扩展与集成

      Docker 的架构适合与其他系统（如 Kubernetes、CI/CD 工具、云平台等）进行集成。

      好处：

      支持构建自动化流水线。

      可以把 Docker 作为底层运行时，构建复杂的容器编排系统。

  1. 除了 Docker，其他容器技术还有 Kata、gVisor、rkt、podman 等，但都不如 Docker 流行。
  2. Docker Desktop 之前一直是可以免费使用的，但在 2021 年 8 月 31 日，Docker 公司改变了策略，只对个人、教育和小型公司免费，其他形式的商业使用需要采用订阅制付费。
  3. busybox 是一个小巧精致的“工具箱”，把诸多 Linux 命令整合在一个可执行文件里，体积一般不超过 2MB，非常适合测试任务或者嵌入式系统。


02｜被隔离的进程：一起来看看容器的本质

容器是什么

  • 广义：容器技术是动态的容器、静态的镜像和远端的仓库这三者的组合
  • 侠义：容器，就是一个特殊的隔离环境，它能够让进程只看到这个环境里的有限信息，不能对外界环境施加影响。（容器就是被隔离的进程）

为什么要隔离（隔离的目的）

  • 系统安全考虑：使用容器技术，我们就可以让应用程序运行在一个有严密防护的“沙盒”（Sandbox）环境之内，从而保证了容器外系统的安全。
  • 资源隔离（限制资源访问）：为应用程序加上资源隔离，在系统里切分出一部分资源，让它只能使用指定的配额，避免容器内进程的过度系统消耗，充分利用计算机硬件，让有限的资源能够提供稳定可靠的服务。

容器 VS 虚拟机

  • 容器是常见的“沙盒”技术中的一种，与虚拟机差不多
  • 容器和虚拟机面对的都是相同的问题，使用的也都是虚拟化技术，只是所在的层次不同

（Docker 官网的图示其实并不太准确，容器并不直接运行在 Docker 上，Docker 只是辅助建立隔离环境，让容器基于 Linux 操作系统运行）

  • 容器和虚拟机的目的都是隔离资源，保证系统安全，然后是尽量提高资源的利用率。
  • 虚拟机虚拟化出来的是硬件，需要在上面再安装一个操作系统后才能够运行应用程序，而硬件虚拟化和操作系统都比较“重”，会消耗大量的 CPU、内存、硬盘等系统资源，但这些消耗其实并没有带来什么价值，属于“重复劳动”和“无用功”，不过好处就是隔离程度非常高，每个虚拟机之间可以做到完全无干扰。
  • 容器（即图中的 Docker），它直接利用了下层的计算机硬件和操作系统，因为比虚拟机少了一层，所以自然就会节约 CPU 和内存，显得非常轻量级，能够更高效地利用硬件资源。不过，因为多个容器共用操作系统内核，应用程序的隔离程度就没有虚拟机那么高了。
  • 运行效率：
    • 虚拟机：资源消耗大，启动慢（其他的资源都用来支持虚拟机运行）
    • 容器：资源利用率高，运行速度快
  • 虚拟机和容器两者并不排斥，可以结合起来使用

隔离是怎么实现的

  • 概述
    • 虚拟机隔离实现：Hypervisor（KVM、Xen 等）
    • 容器隔离实现：namespace、cgroup、chroot
  • namespace
    • namespace 是 2002 年从 Linux 2.4.19 开始出现，可以创建出独立的文件系统、主机名、进程号、网络等资源空间，实现了系统全局资源和进程局部资源的隔离。
  • cgroup
    • cgroup 是 2008 年从 Linux 2.6.24 开始出现的，它的全称是 Linux Control Group，用来实现对进程的 CPU、内存等资源的优先级和配额限制
  • chroot
    • chroot在 1979 年的 UNIX V7 就已经出现了，可以更改进程的根目录，也就是限制访问文件系统

思考题

  1. 有一种说法：容器就是轻量级的虚拟机，你认为这种说法正确吗？

“容器就是轻量级的虚拟机”——这句话有一定道理，但不完全准确

  • 为什么说它“有一定道理”：
    • （1）都能隔离运行环境
    • （2）都能实现快速部署
    • （3）都用于资源复用和环境一致性
  • 为什么说这并不准确：
    • 容器不是模拟硬件，而是复用宿主操作系统的内核。
    • 容器不像虚拟机那样运行一个完整的 Guest OS，而是运行在宿主机内核空间内。
项目 虚拟机 容器
启动速度 慢（几分钟） 快（秒级）
系统资源 占用大（完整操作系统） 占用小（共享宿主内核）
内核隔离 是（每个虚拟机有自己内核） 否（共享宿主机的内核）
安全隔离 更强（真正的系统级隔离） 相对较弱（依赖内核命名空间）
技术原理 基于 硬件虚拟化（如 KVM） 基于 操作系统内核隔离（如 namespace, cgroups）

扩展

  1. Alpine Linux 是一个微型的 Linux 发行版，体积很小，注重安全和效率。
  2. cgroup 技术最早由 Google 实现，被用于公司内部的 Borg 系统，也就是 Kubernetes 的前身，后来才被集成进 Linux 内核。
  3. 当前的容器基本不再使用过于古老的 chroot 了，而是改用 pivot_root。
  4. 早期的 Docker 内部使用的技术是 LXC（Linux Containers），后来改成了自己研发的 libcontainer，现在则是基于 containerd 和 runc。
  5. 虚拟化 是计算机界的一门传统技术，例如虚拟 CPU、虚拟内存、虚拟磁盘、虚拟网卡等等，其目的是资源共享，提高资源利用率。


03｜容器化的应用：会了这些你就是Docker高手

什么是容器化的应用

  • 镜像

    • 只读，不允许修改，以标准格式存储了一系列的文件，然后在需要的时候再从中提取出数据运行起来。
    • 它里面不仅有基本的可执行文件，还有应用运行时的整个系统环境。这就让镜像具有了非常好的跨平台便携性和兼容性
    • 镜像的完整名字由两个部分组成，名字和标签，中间用 : 连接起来。

  • 容器化的应用（应用的容器化）

    • 是指应用程序不再直接和操作系统打交道，而是封装成镜像，再交给容器环境去运行。

镜像就是静态的应用容器，容器就是动态的应用镜像


思考题

  • 说一说你对容器镜像的理解，它与 rpm、deb 安装包有哪些不同和优缺点

    容器镜像的基本理解：

    容器镜像是一种轻量级、可移植、自包含的软件打包格式，包含运行某个软件所需的全部内容，包括：

    • 应用程序二进制文件
    • 所有依赖库
    • 系统工具、配置
    • 基础操作系统层（例如 Alpine、Debian）

    镜像是只读层，容器运行时会在其上加一个可写层。镜像的本质是多个文件系统层（layer）的组合。

    容器镜像 VS rpm/deb 安装包

    特性 容器镜像（Container Image） RPM/DEB 包
    内容 包含完整运行环境 只包含软件二进制及依赖元数据
    作用对象 运行时环境（Runtime） 安装在宿主操作系统上
    是否隔离 有（通过容器技术） 无（直接安装在系统中）
    安装依赖方式 内部打包依赖（自包含） 依赖操作系统包管理器
    部署方式 快速启动，可跨平台迁移 启动慢，系统依赖强
    可移植性 高（可在任何支持容器的主机运行） 低（依赖特定发行版和版本）
    管理工具 Docker、Podman、CRI-O yum/dnf（RPM）、apt（DEB）
    更新方式 镜像替换或重构 增量更新依赖包

  • 你觉得 docker run 和 docker exec 的区别在哪里，应该怎么使用它们？

    它们的主要区别在于作用对象和使用时机不同

    特性 docker run docker exec
    作用对象 镜像（Image） 已运行的容器（Container）
    用途 创建并启动一个新的容器 在现有的容器中执行命令
    容器状态 创建新的 必须已运行
    是否新容器 是 否（复用现有容器）
    使用频率 启动容器 调试、执行临时命令
    示例 docker run -it ubuntu bash docker exec -it my_container bash


04｜创建容器镜像：如何编写正确、高效的Dockerfile

镜像是怎么创建出来的？我们能不能够制作属于自己的镜像呢？(解剖镜像的内部机制，熟悉高效、正确地编写 Dockerfile 制作容器镜像的方法)

镜像的内部机制是什么

  • 镜像就是一个打包文件，里面包含了应用程序还有它运行所依赖的环境，例如文件系统、环境变量、配置参数等等。
  • 容器镜像的一个重大创新点：分层，术语叫“Layer”
  • 容器镜像是由多个只读的 Layer 构成的，同一个 Layer 可以被不同的镜像共享，减少了存储和传输的成本。
    • 容器镜像内部并不是一个平坦的结构，而是由许多的镜像层组成的，每层都是只读不可修改的一组文件，相同的层可以在镜像之间共享，然后多个层像搭积木一样堆叠起来，再使用一种叫“Union FS 联合文件系统”的技术把它们合并在一起，就形成了容器最终看到的文件系统
  • 可以用命令 docker inspect 来查看镜像的分层信息
  • 在使用 docker pull、docker rmi 等命令操作镜像的时候，如果本地已经存在就不会重复下载，如果层被其他镜像共享就不会删除，这样就可以节约磁盘和网络成本。

Dockerfile 是什么

  • Dockerfile类似于施工图纸
  • Dockerfile 非常普通，它就是一个纯文本，里面记录了一系列的构建指令，比如选择基础镜像、拷贝文件、运行脚本等等，每个指令都会生成一个 Layer，而 Docker 顺序执行这个文件里的所有步骤，最后就会创建出一个新的镜像出来。

怎样编写正确、高效的 Dockerfile

  • 构建镜像的第一条指令必须是 FROM
    • 基础镜像的选择非常关键
    • 如果关注的是镜像的安全和大小，那么一般会选择 Alpine
    • 如果关注的是应用的运行稳定性，那么可能会选择 Ubuntu、Debian、CentOS

  • 指令 RUN ，它可以执行任意的 Shell 命令，比如更新系统、安装应用、下载文件、创建目录、编译程序等等，实现任意的镜像构建步骤，非常灵活

  • 可以把这些 Shell 命令集中到一个脚本文件里，用 COPY 命令拷贝进去再用 RUN 来执行：

  • 可以实现参数化运行，这在 Dockerfile 里也可以做到，需要使用两个指令 ARG 和 ENV

    • ARG 创建的变量只在镜像构建过程中可见，容器运行时不可见
    • ENV 创建的变量不仅能够在构建镜像的过程中使用，在容器运行时也能够以环境变量的形式被应用程序使用

  • EXPOSE，它用来声明容器对外服务的端口号。EXPOSE 并不会真的映射端口，它只是一个文档型声明。实际端口映射需要通过 docker run -p 实现。

  • 因为每个指令都会生成一个镜像层，所以 Dockerfile 里最好不要滥用指令，尽量精简合并，否则太多的层会导致镜像臃肿不堪。


docker build 是怎么工作的

  • 命令行“docker”是一个简单的客户端，真正的镜像构建工作是由服务器端的“Docker daemon”来完成，“docker”客户端就只能把“构建上下文”目录打包上传（显示信息 Sending build context to Docker daemon ），这样服务器才能够获取本地的这些文件
  • 可以在“构建上下文”目录里再建立一个 .dockerignore 文件，语法与 .gitignore 类似，排除那些不需要的文件
  • -f 显示指定Dokerfile文件，不使用这个参数则默认指 Dockerfile
  • -t 指定镜像标签

思考题

  • 镜像里的层都是只读不可修改的，但容器运行的时候经常会写入数据，这个冲突应该怎么解决呢？

    镜像的每一层是只读的（read-only），而容器运行时会增加一个可写层（writeable layer）来解决这个冲突


扩展

  1. 我们也可以使用命令 docker commit 从运行中的容器直接生成镜像，但这样不具有 Dockerfile “文档化”的优点，一般不推荐使用。
  2. Docker 镜像遵循的是 OCI（Open Container Initiative）标准，所以制作出来的镜像文件也能够被其他的容器技术（如 Kata、Kubernetes）识别并运行。
  3. Union FS 有多种实现，例如 aufs、btrfs、device-mapper 等，目前 Docker 使用的是 overlay2，可以在 docker info 中查看。
  4. Dockerfile 里的构建指令不区分大小写，例如 “FROM” 也可以写成 “from”，但习惯上都使用大写形式。
  5. 在 Dockerfile 里还可以使用另一个与 “COPY” 很类似的 “ADD” 指令，它不仅能够拷贝文件，还支持下载和自动解压压缩，但过多的操作让它的含义比较模糊，不容易控制，个人不推荐使用。
  6. “ENTRYPOINT” 是一个与 “CMD” 类似的指令，也可以定义启动命令，相当于 docker run xxx ENTRYPOINT CMD，不过没有 “CMD” 常用。
  7. 可以使用 docker history 命令回放完整的镜像的构建过程，有的时候对于镜像排错很有用。


05｜镜像仓库：该怎样用好Docker Hub这个宝藏

镜像文件应该如何管理

什么是镜像仓库（Registry）

  • Registry
  • 拉取镜像、它还会提供更多的功能，比如上传、查询、删除等等，是一个全面的镜像管理服务站点。

什么是 Docker Hub

  • 使用 docker pull 获取镜像的时候，Docker 会使用一个默认的镜像仓库：Docker Hub
  • Docker Hub 是 Docker 公司搭建的官方 Registry 服务，创立于 2014 年 6 月，和 Docker 1.0 同时发布。它号称是世界上最大的镜像仓库，和 GitHub 一样，几乎成为了容器世界的基础设施。
  • Docker Hub 已经不再是一个单纯的镜像仓库了，更应该说是一个丰富而繁荣的容器社区。

如何在 Docker Hub 上挑选镜像

  • 在 Docker Hub 上有官方镜像、认证镜像和非官方镜像的区别。
    • 官方镜像：是指 Docker 公司官方提供的高质量镜像
    • 认证镜像：标记是“Verified publisher”，也就是认证发行商，比如 Bitnami、Rancher、Ubuntu 等。
    • 非官方镜像：
      • “半官方”镜像：成为“Verified publisher”是要给 Docker 公司交钱的，而很多公司不想花这笔“冤枉钱”，所以只在 Docker Hub 上开了公司账号，但并不加入认证。
      • 纯粹的“民间”镜像
  • 使用 docker pull 下载这些非官方镜像的时候，就必须把用户名也带上，否则默认就会使用官方镜像

Docker Hub 上镜像命名的规则是什么

  • 直接使用默认的“latest”虽然简单方便，但在生产环境里是一种非常不负责任的做法，会导致版本不可控
  • 通常来说，镜像标签的格式是应用的版本号加上操作系统。
  • 有的标签还会加上 slim、fat，来进一步表示这个镜像的内容是经过精简的，还是包含了较多的辅助工具。通常 slim 镜像会比较小，运行效率高，而 fat 镜像会比较大，适合用来开发调试。

该怎么上传自己的镜像

  1. 在 Docker Hub 上注册一个用户
  2. 使用 docker login 命令，用刚才注册的用户名和密码认证身份登录
  3. 使用 docker tag 命令，给镜像改成带用户名的完整名字，表示镜像是属于这个用户的。或者简单一点，直接用 docker build -t 在创建镜像的时候就起好名字（docker tag ngx-app chronolaw/ngx-app:1.0）
  4. 用 docker push 把这个镜像推上去（docker push chronolaw/ngx-app:1.0）

离线环境该怎么办

  • 在内网环境里仿造 Docker Hub，创建一个自己的私有 Registry 服务，由它来管理我们的镜像；自建 Registry 已经有很多成熟的解决方案，比如 Docker Registry，还有 CNCF Harbor
  • Docker 提供了 save 和 load 这两个镜像归档命令，可以把镜像导出成压缩包，或者从压缩包导入 Docker，而压缩包是非常容易保管和传输的，可以联机拷贝，FTP 共享，甚至存在 U 盘上随身携带。用 -o、-i 参数来使用文件的形式

思考题

  • 很多应用（如 Nginx、Redis、Go）都已经有了 Docker 官方镜像，为什么其他公司（Bitnami、Rancher）还要重复劳动，发布自己打包的镜像呢？

    1. 定制化需求
    2. 安全 & 合规性
    3. 统一生态与平台集成
    4. 多架构、多发行版支持
    5. 服务商业化和品牌影响力

06｜打破次元壁：容器该如何与外界互联互通

如何拷贝容器内的数据


如何共享主机上的文件

-v 参数挂载宿主机目录的这个功能，对于我们日常开发测试工作来说非常有用，我们可以在不变动本机环境的前提下，使用镜像安装任意的应用，然后直接以容器来运行我们本地的源码、脚本，非常方便。


如何实现网络互通

  • Docker 提供了三种网络模式，分别是 null、host 和 bridge。

  • null

    • 是最简单的模式，也就是没有网络，但允许其他的网络插件来自定义网络连接，这里就不多做介绍了。

  • host

    • host 的意思是直接使用宿主机网络，相当于去掉了容器的网络隔离（其他隔离依然保留），所有的容器会共享宿主机的 IP 地址和网卡。
    • 这种模式没有中间层，自然通信效率高，但缺少了隔离，运行太多的容器也容易导致端口冲突。

  • bridge*（桥接模式）

    • 类似现实世界里的交换机、路由器，只不过是由软件虚拟出来的，容器和宿主机再通过虚拟网卡接入这个网桥
    • 它们之间也就可以正常的收发网络数据包了。不过和 host 模式相比，bridge 模式多了虚拟网桥和网卡，通信效率会低一些。
    • Docker 默认的网络模式就是 bridge，所以一般不需要显式指定。（也可以用 –net=bridge 来启用桥接模式）

如何分配服务端口号

  • 可以用 EXPOSE 指令声明容器对外的端口号
  • 由容器环境例如 Docker 来统一管理分配端口号，在本机端口和容器端口之间做一个“映射”操作，容器内部还是用自己的端口号，但外界看到的却是另外一个端口号，这样就很好地避免了冲突。
  • 端口号映射需要使用 bridge 模式，并且在 docker run 启动容器时使用 -p 参数，形式和共享目录的 -v 参数很类似，用 : 分隔本机端口和容器端口。
  • 端口号映射需要使用 bridge 模式，并且在 docker run 启动容器时使用 -p 参数，形式和共享目录的 -v 参数很类似，用 : 分隔本机端口和容器端口。
  • 使用 docker ps 命令能够在“PORTS”栏里更直观地看到端口的映射情况

思考题

  1. docker cp 命令和 Dockerfile 里的 COPY 指令有什么区别？
特性 COPY（Dockerfile） docker cp（命令行）
使用时机 构建镜像时 容器运行时
操作对象 镜像层中的文件系统 正在运行的容器或容器生成的文件系统
数据方向 主机 → 镜像 主机 ↔ 容器
是否可双向复制 否 是
是否影响镜像 是 否（仅容器）
常见用途 镜像构建时添加文件 容器调试、导入导出、应急修复
  1. host 模式和 bridge 模式各有什么优缺点，在什么场景下应用最合适？

docker 的 --network 网络模式中，最常用的两种模式是：

  • bridge（桥接）模式（默认）
  • host（主机）模式

这两种网络模式的核心区别在于：容器与宿主机之间的网络隔离程度不同。

  • Bridge 模式（默认网络）
    • 工作原理：Docker 会在宿主机上创建一个虚拟网桥（如 docker0），每个容器分配一个私有 IP，并通过 NAT 转换与外部通信。
    • 容器 (172.17.0.X) -> docker0 网桥 -> 宿主机网络 (eth0)
    • 优点：
      • 网络隔离强：容器有独立 IP，互相隔离，安全性更高
      • 更灵活：支持端口映射（-p 或 -P），可以自由控制暴露的端口
      • 容器间通信可控：可以通过自定义 bridge 网络让容器互通或隔离
    • 缺点：
      • 性能略低：多了一层 NAT，网络性能略逊
      • 配置略复杂：某些需要真实 IP 的服务（如某些数据库集群）配置较麻烦
    • 适用场景：
      • 日常开发、测试环境
      • 微服务部署场景
      • 多个容器共享网络但仍需隔离
  • Host 模式（–network host）
    • 工作原理：容器不再虚拟出自己的网络空间，而是直接使用宿主机的网络。容器中的服务监听的端口，其实就是宿主机的端口。
    • 容器与宿主机共享网络栈：容器内 ifconfig ≈ 宿主机 ifconfig
    • 优点：
      • 性能最高：没有 NAT 转换，直接使用主机网络
      • 配置简单：服务无需做端口映射，可直接监听主机端口
      • 兼容性更强：某些依赖宿主机网络的服务（如 mDNS、DHCP、广播）可正常运行
    • 缺点：
      • 安全性低：容器对主机网络无隔离，存在更高风险
      • 端口冲突：容器与宿主机共享端口，容易冲突
      • 多实例部署困难：同一台主机上不能同时运行多个监听同端口的容器
    • 适用场景：
      • 性能要求极高的场景（如高频交易系统）
      • 需要与宿主机网络强耦合的服务（如 Prometheus 监控 node_exporter）
      • 网络功能型容器（如 VPN、SDN 插件、网络采集工具）
  • 实际应用建议对比
维度 Bridge 模式 Host 模式
网络隔离性 ✅ 强 ❌ 无
性能 中等（有 NAT） ✅ 高（无 NAT）
安全性 ✅ 高（端口可控） ❌ 低（共享网络）
端口冲突风险 ✅ 可避免 ❌ 易冲突
多实例部署 ✅ 可通过端口映射部署多个 ❌ 监听同一端口会冲突
使用场景 一般服务、Web 应用、微服务 网络工具、监控探针、需要全网访问的服务
  • 如果你不知道用哪种模式，就用 bridge；只有在你明确知道为什么需要 host 模式时，才使用 host。

扩展

  1. Docker 还可以使用“volume”命令创建独立挂载的“数据卷”，但它的用法与 Kubernetes 差距较大，为了避免混淆这里就不介绍了。
  2. Docker 官方推荐使用“–mount”来代替“-v”，但“–mount”用法很繁琐，而“-v”已经有了很长的应用历史了，所以我还是建议用较为方便的“-v”。
  3. “-v”挂载目录时如果发现源路径不存在会自动创建，这个时候会是一个“坑”，当主机目录被意外删除时会导致容器里出现空目录，让应用无法按预想的流程工作。
  4. “-v”挂载目录默认是可读可写的，但也可以加上“:ro”变成只读，可以防止容器意外修改文件，例如“-v /tmp:/tmp:ro”。
  5. IPv4 地址是 32 位，分为 5 类（ABCDE），ABC 类地址中各有一部分网段可以私用，“172.16.0.0/16 ~ 172.31.0.0/16”就都属于 B 类私有地址。
