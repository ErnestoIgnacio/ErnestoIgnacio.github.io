极客时间专栏《深入浅出分布式技术原理》（陈现鳞）Study Notes


开篇词 (1讲)

开篇词｜掌握好学习路径，分布式系统原来如此简单

概述

  • 分布式架构已经成为互联网公司IT架构的事实标准

    • 学习和理解分布式系统是值得投入的一件事
    • 是否理解分布式系统是区分初级和资深工程师的重要指标

  • 在分布式系统中，站在不同层面会看到不同的分布式系统

    • 单一应用层面：单体服务和多服务的分布式系统
    • 公司层面：单机房、多机房或者跨洲际的分布式系统
    • 整个互联网层面：基于 TCP/IP 协议构建的整个互联网，就是一个超大规模的分布式系统

  • 经验之谈：

    初学者想要高效且系统性地掌握分布式系统，这本身就是一个悖论。不管你有多努力，要知道理论与实践之间是有一道巨大的鸿沟的。你很可能会被场景、时间、自身积累与理解程度等原因限制住，导致学习事倍功半，实践也效率低下。而对于这个主题来说，论文、源码等资料的学习仅仅是入门，我们还需要结合业务场景、工作经历和实践经验，再加上思考与时间去慢慢沉淀才可以。

  • 学习经验：

    • 一定要有一条明确的学习路径，从最根本的原因出发
      • 多问自己为什么，然后再思考怎么做。在技术理解与实践中反复横跳，才能由点成线
      • 在总结中抓住技术实现的关键点和系统脉络，不迷失于细节，才能连线成网

课程设计

  • （1）找到分布式系统中稳定不变的知识、原理和解决思路
    • 比如注册发现的原理、故障处理的思路和 CAP 理论等等
    • 万变不离其宗，掌握核心，一通百通
  • （2）去繁从简
    • 聚焦于日常工作中接触最频繁的在线业务分布式系统：分布式计算、分布式存储（不会讨论分布式批处理和流计算）

概述篇

  • 理解这个知识的来龙去脉：讨论分布式系统产生的过程，它为什么会产生，产生后解决了什么问题，又带来了哪些新问题，遇到哪些方面的挑战
  • 抓到分布式系统的脉络和关键点：有了很强的学习目标和路径。不迷失在细节中

分布式计算篇

  • 分布式计算是日常工作中接触最多的分布式技术
  • 从单机系统演进到分布式系统后，引入哪些新问题的角度，在技术原理层面一个一个讨论并解决这些问题
  • 学习之后：可以在各种系统和场景中理解和运用它，并且知道在系统设计层面应该如何取舍

分布式存储篇

  • 分布式技术篇中的进阶篇
  • 讨论数据分片、数据复制、分布式事务和一致性等相关的知识
  • 掌握之后：再做架构设计时，会发现思维的深度和广度都得到了提升

总结篇

  • 一起来看分布式系统的发展历程和未来趋势：
    • 讨论分布式系统是怎么从单机系统演进到 Service Mesh
    • 讨论分布式系统是怎么从单机系统的 ACID 演进到NewSQL



概述篇 (3讲)

01｜导读：以前因后果为脉络，串起网状知识体系

Tips

  • 学习一个知识前，比较好的方式是理解它的前因后果
    • 前因：这个知识产生的过程中，解决了什么问题？怎么解决的？
    • 后果：它的出现带来了哪些新的问题？

前因：分布式系统解决了什么问题

  • 分布式系统解决了单机性能瓶颈导致的成本问题
  • 解决了用户量和数据量爆炸性地增大导致的成本问题
  • 单机系统可以支撑的服务，因为要满足高可用的要求，也会变成一个分布式系统
  • 分布式系统解决了大规模软件系统的迭代效率和成本的问题

单机系统是无法解决成本、效率和高可用问题的


分布式系统是怎么解决单机系统面临的成本、效率和高可用的问题？

  • 将一些廉价的 PC 机，通过网络连接起来共同完成工作，并且在系统中提供冗余，来解决高可用的问题
  • 分布式系统是通过多工作节点，来解决单机系统面临的成本、效率和高可用问题的

理解分布式系统

  • 如何理解分布式系统的出现：我们可以把分布式系统看成是单体系统的平民化和物美价廉的版本
  • 分布式系统在不同业务场景中的表现形式
    • 流量路由策略加多副本部署（微服务是其中的一种架构形式）是无状态服务的分布式架构方案
    • Redis Cluster 和 Codis 等方案实现了缓存的分布式化
    • Kubernetes 则完成了操作系统的分布式进化
    • NoSQL 掀起了数据库分布式化的第一波浪潮，NewSQL 则推动着支持 ACID 的关系数据库的分布式化

后果：如何思考和处理分布式系统引入的新问题

分布式计算（无状态）的情况

  • （1）怎么找到服务？

服务注册与发现机制是常用的思路，可以理解服务注册发现机制的实现原理，并且思考一下服务注册发现，是选择做成 AP 系统还是 CP 系统更合理

  • （2）怎么找到实例？

如果同一个服务的实例是完全对等的（无状态），那么按负载均衡的策略来处理就足够（轮询、权重、Hash、一致性 Hash，FAIR 等各种策略的适用场景）

如果同一个服务的实例不对等（有状态），那么就需要通过路由服务（元数据服务等）确定，当前要访问的请求数据做到哪一个实例上，然后再进行访问

  • （3）怎么管理配置？

一般的思路是通过一个中心化的存储来统一管理系统的配置，即配置中心

  • （4）怎么进行协同？

通过一个跨进程与机器的分布式锁来解决

  • （5）怎么确保请求只执行一次？（在分布式系统中，各个模块之间通过网络进行连接。如果出现了网络抖动等情况，会导致模块之间的调用失败，而调用失败就有可能触发重试策略，使得程序可能出现没有执行或者多次执行的情况）

重试加上幂等是分布式系统中，确保请求只执行一次的方法

  • （6）怎么避免雪崩？（系统雪崩是指由于正反馈循序导致不断扩大规则的故障。一次雪崩通常是由于整个系统中，一个很小的部分出现故障而引发，进而导致系统的其他部分也出现故障。）

一个是快速失败和降级机制（熔断、降级、限流等），通过快速减少系统负载来避免雪崩的发生（对一致性要求很高的话，快速失败会带来系统数据不一致的问题）

另一个是弹性扩容机制，通过快速增加系统的服务能力来避免雪崩的发生（实现成本比快速失败要大，响应时间也更长）

  • （7）怎么监控告警和故障恢复？

对于一个分布式系统来说，如果我们不能清楚地了解内部的状态，那么系统的稳定性是没有办法完全保障的。所以我们一定要完善分布式系统的监控（比如接口的时延和可用性等信息），分布式追踪 Trace ，模拟故障的混沌工程以及相关的告警等机制。同时做好故障恢复预案，确保在故障发生的时候，能够快速恢复故障

分布式存储（有状态）

  • CAP 及其相关理论与权衡方面，需要了解 ACID 、 BASE 和 CAP 理论这三个主题

    • 参考文献
      • CAP Twelve Years Later: How the “Rules” Have Changed
      • CAP 理论十二年回顾：”规则”变了

  • 思考怎么做数据分片？（单机系统是不可能存储所有数据的，所以需要解决怎么将数据按一定的规则，分别存储到不同的机器上这个问题）

Hash 和 Region 分片的策略，要注意了解一下它们的优缺点和各自的应用场景

  • 怎么做数据复制？（为了满足系统的高可用要求，需要对数据做冗余处理）

中心化方案（主从复制、一致性协议，比如 Raft 和 Paxos等）

去中心化的方案（ Quorum 和 Vector Clock）

需要了解它们的优缺点，各自的应用场景，以及对系统外部表现出来的数据一致性级别（线性一致性、顺序一致性、最终一致性等）

  • 怎么做分布式事务？

对于分布式系统来说，要实现事务，首先需要对并发事务进行排序的能力，这样在事务冲突的时候，就可以确认哪个事务提交成功，哪个事务提交失败。参考Google 的 Spanner ，它是通过 GPS 和原子钟，实现 TrueTime API 来解决这个问题，从而实现全球分布式数据库的

有了事务 ID 后，通过 2PC 或者 3PC 协议来实现分布式事务的原子性


总结：如何系统学习分布式知识

从实践出发（研究目前比较常用的分布式系统的设计）

  • HDFS 或者 GFS（分布式文件系统）
  • Kafka 和 Pulsar（分布式消息队列）
  • Redis Cluster 和 Codis（分布式缓存）
  • MySQL 的分库分表（传统关系型数据库的分布式方案）
  • MongoDB 的 Replica Set 和Sharing 机制集（NoSQL 数据库）
  • TiDB（NewSQL）
  • 一些微服务框架

从理论出发

  • 研究分布式相关的论文
  • 参考书籍推荐：《 Designing Data-IntensiveApplications 》

分布式系统问题的总结

路由问题
  • 正常情况下的路由问题：
    • 服务注册发现和负载均衡的问题
    • 怎么找到服务
    • 怎么找到实例
  • 带状态的路由问题：
    • 怎么做数据分片
  • 异常情况下的路由问题：
    • 怎么避免雪崩
    • 熔断、降级等快速失败和降级机制
共识问题
  • 怎么做数据复制
  • 怎么做分布式事务
  • 怎么做分布式锁
运维问题
  • 怎么配置管理
  • 怎么监控告警和故障恢复


02｜新的挑战：分布式系统是银弹吗？我看未必！

概述

  • 分布式系统和单体系统的本质差别：
    • 单体系统是以单进程的形式运行在一个计算机节点上，分布式系统是以多进程的形式运行在多个计算机节点上。
    • 二者的本质差别导致了分布式系统面临的四个方面的问题：
      • 故障处理
      • 异步网络
      • 时钟同步
      • 共识协同

探讨分布式系统会面临哪些新的挑战，而这些挑战又是怎么影响分布式系统的架构和设计


故障处理：全部失败与部分失败

  • 分布式系统由多个计算机节点组成，虽然每一个计算机节点都是全部失败的模型，但是如果系统中的某些节点出现宕机或者网络故障，整个分布式系统就会出现部分失败的情况，单机计算机系统这个确定性的全部失败的模型，在分布式系统中就无效了。这个问题大大增加了分布式系统的复杂性，也给我们处理分布式问题提高了难度
  • 部分失败的情况是构建分布式系统的一个大挑战，也深刻影响着分布式系统的设计方式和原则
  • 在分布式系统中，我们需要接受部分失败，接受系统中每一个部分可能出现故障的情况，在不可靠的硬件上通过软件来容错，构建高可用的分布式系统
  • 在分布式系统中，故障处理是软件设计的一个重要组成部分。我们需要时刻谨记节点宕机、网络分区等各种问题出现时，系统应该怎么正确处理，比如分布式系统在设计的时候，每一个组件都必须是高可用的
  • 在网络出现分区的时候，系统必须能够正确处理，在网络分区恢复的时候，系统也必须正确处理，不能出现不可预知的错误，特别是在进行数据复制的时候

异步网络：本地调用与远程调用

  • 在单机系统中，系统各个组件之间的调用方式非常简单，直接本地调用即可
  • 在分布式系统中，不同的组件运行在不同的机器上，通过本地调用是不可行的，我们只能通过网络来进行调用，即远程调用
  • 远程调用是通过网络来发送数据的，而我们目前依赖的网络是异步的，从一个节点发送数据到另一个节点，不能保证在多少时间内到达，甚至不能保证一定能到达
  • 远程调用在时间上有不确定性
  • 在这样的情况下，通常的做法是采用超时机制，请求方在发起请求后，设置一个超时时间，这样能确保请求方在超时时间内，一定能得到一个响应
  • 如果请求在超时时间内没有收到任何响应，即响应超时，那么调用方将无法区分下面四种情况
    • 请求丢失了
    • 请求由于在网络中排队而导致超时了，但是最终依然会收到
    • 响应丢失了
    • 响应由于在网络中排队而导致超时了，但是最终依然会收到
  • 在分布式系统的设计中，我们要充分考虑通过网络进行远程调用导致的不确定性，比如在响应超时的情况下增加重试机制，确保请求能最少执行一次。在重试的时候增加幂等的机制，确保请求只被精确处理一次，并且对重试机制增加退避策略，确保系统不会因为重试导致雪崩

时钟同步

计算机系统一般是通过石英钟来计算时间的，但是石英钟的振动频率会随着温度等原因变慢或变快，所以在运行时间比较长后，计算机系统的时间可能会发生比较大的误差，所以人们又增加了一组专门的时间服务器。我们可以认为这些时间服务器的时间是准确的，计算机系统通过网络定期获得时间服务器的时间，来调整本地时间，即网络时间协议（NTP）。我们可以通过下面的公式来计算当时的时间：

本地时间 = 时间服务器的返回时间 + 时间服务器响应的网络时延

  • 计算机系统中，时间主要有两个作用
    • 计算机系统中，时间主要有两个作用计算机系统中，时间主要有两个作用
    • 记录事件之间的发生顺序，这是一个相对时间
  • 如果我们都采用本地的时钟来记录事件的发生时间，然后基于多个节点上的事件按发生时间进行排序，就很容易出现时间穿越的问题
  • 在分布式系统的设计中，我们一定要谨记系统中各个节点的本地时钟是存在误差的，不能依赖各自的时钟对事件进行排序。解决思路：
    • 去请求同一个时间服务器获得事件的发生时间，然后依据这个时间进行排序
    • Google 在 Spanner 中使用的，通过 GPS 和原子钟实现 TrueTime API 来解决

共识协同：一言堂与共识

在单体系统中，需要协同的多个线程是属于同一个进程的，所以同步操作很简单，直接使用进程内的资源来做协同就可以了，比如锁、信号量等。对于这些线程来说，所有的同步操作都以进程的资源为准，就好像进程是一个一言堂的管理员，协同进程内部的所有线程之间的同步

  • 对于分布式系统来说，我们需要处理的是一个跨机器的多进程同步问题
  • 选择一个服务来做同步操作的管理者（我们称为同步服务），在多个进程间需要同步时，就到同步服务来请求一个锁，获得锁的进程就可以操作，其他的进程就必须等待（必须要考虑到故障的存在）
  • 这是一个共识问题，需要分布式系统中参与同步的进程之间能达成共识，目前我们是通过 Paxos 或者 Raft 这样的共识算法来解决问题的

春节加餐 (3讲)

春节加餐｜系统性思维，高效学习和工作的利器

学习和工作是人生中非常关键和重要的2个部分，它们占据了我们的大部分时间。并且它们的结果也在很大程度上决定了我们生活的幸福感和生活质量。在同样时间里，如果让学习和工作变得高效，就是我们自我提升的关键了。


对于学习，从深度和广度上运用系统性思维方式

  • 学习计算机技术知识面临的两大问题：
    • 知识抽象，不好理解（如果跳过了这个知识产生的时代背景和原因，在深度的学习上就缺乏了系统性）
      • 解决方案：我们要知道一个知识是为了解决什么问题而产生的，后面又经过了什么样的迭代和优化，最终演变成了什么样子
    • 学习后容易忘记（因为在广度的学习上缺乏了系统性）我们学习了很多零散的知识，但是却没有将知识点之间建立起联系，形成一个相互依赖的网状知识体系
      • 解决方案：将知识点之间建立起联系，形成一个相互依赖的网状知识体系
  • 两个问题的原因是：学习方式不够系统

对于工作，通过系统性思维从根本上解决问题

  • 我们在每一次面对独立的问题的时候，应该跳过问题表层现象，深度思考这个问题的本质原因，系统性地解决
